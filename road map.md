# Дорожная карта разработки 2D-движка

**Цель:** разработать с нуля автономный 2D-движок на C++ для **Windows и Linux** с минимальным набором локально размещённых сторонних библиотек только для изображений и аудио. Движок должен охватывать полный цикл создания небольшой 2D-игры: управление окном и вводом, рендеринг, загрузку ресурсов, спрайты, анимацию, шрифты, GUI, сцены и игровые объекты, столкновения, физику, события и сценарии поведения, звук, сохранения и локализацию. **После приёмки движка** на его основе планируется разработка 2D-платформера.

Документ — **самостоятельный план реализации**, а не описание существующей кодовой базы. Он задаёт необходимые возможности, очерёдность их появления, зависимости и критерии приёмки. Для каждого этапа нужен работающий демонстрационный сценарий; одного набора заголовков или незаполненных интерфейсов недостаточно. Реализация ведётся небольшими проверяемыми изменениями с помощью ИИ.

## 1. Требования к движку и правила реализации

### Целевое окружение

- **Язык:** C++17; **сборка:** CMake. Для тестирования допускаются собственные небольшие тестовые программы без внешнего тестового фреймворка.
- **Графика:** OpenGL 1.1. Не требовать шейдеров, VBO/VAO и других возможностей новых версий OpenGL. Работа с OpenGL должна быть скрыта за интерфейсом 2D-рендеринга.
- **Windows:** платформенный код через Win32/WGL; **Linux:** через X11/GLX. Нативный Wayland и мобильные платформы пока не входят в область поддержки.
- **Зависимости:** стандартная библиотека C++, системные API Windows/Linux и две разрешённые сторонние библиотеки: **stb_image** для декодирования PNG и **miniaudio** для аудио. Исходники этих библиотек и тексты лицензий хранятся в репозитории в `third_party/`; загрузка пакетов из сети при сборке не допускается. Остальные подсистемы (окна, рендеринг, физика, GUI, сцены, сериализация и др.) реализуются самостоятельно. Дополнительные зависимости — только после явного изменения требований.
- **Структура:** `third_party/stb/` и `third_party/miniaudio/` находятся рядом с исходниками движка, а не устанавливаются глобально. Зафиксировать версии/коммиты, лицензии и правила обновления. Включать реализацию однозаголовочных библиотек ровно в одном `.cpp` на библиотеку, скрывать сторонние типы за API движка. Учитывать системные библиотеки, которые аудиобэкенд может динамически использовать в Linux, и проверять запуск на целевых дистрибутивах.
- **Ассеты:** для демонстраций использовать собственные минимальные изображения, атласы, растровые шрифты, PCM WAV и текстовые файлы.

### Размещение и подключение сторонних библиотек

**Обязательное решение:** `stb_image` и `miniaudio` поставляются **вместе с исходниками движка**. Это исключения из правила самостоятельной реализации подсистем: они решают конкретные задачи декодирования изображений и аудиовывода, но не определяют архитектуру движка. Их не надо устанавливать на компьютер разработчика через пакетный менеджер, скачивать в CMake или размещать в системных каталогах. Библиотеки лежат рядом с основной кодовой базой и собираются как часть проекта.

Рекомендуемая структура (названия папок основного проекта можно адаптировать под существующий репозиторий):

```text
project/
├── CMakeLists.txt
├── engine/                 # Собственные исходники и интерфейсы движка
├── platform/               # Windows/Linux платформенные реализации
├── third_party/
│   ├── stb/
│   │   ├── stb_image.h     # Зафиксированная копия stb_image
│   │   └── LICENSE        # Условия использования / атрибуция
│   ├── miniaudio/
│   │   ├── miniaudio.h     # Зафиксированная копия miniaudio
│   │   └── LICENSE        # Условия использования / атрибуция
│   └── README.md          # Источники, версии/коммиты, лицензии, обновление
├── tests/
├── demos/
└── assets/
```

Правила интеграции:

1. **Добавление в репозиторий:** один раз скачать исходники из официальных проектов, убедиться в лицензии и использовать исходники выбранной версии или commit hash. Сохранить вместе с исходниками требуемые тексты лицензий; не полагаться на ссылку как на единственный источник лицензии. На обычной машине сборки сетевой доступ не требуется.
2. **Компиляция:** подключать заголовки из локального каталога через CMake и собирать реализации библиотек в **отдельных единицах трансляции**, например `stb_image_impl.cpp` (`#define STB_IMAGE_IMPLEMENTATION`) и `miniaudio_impl.cpp` (`#define MINIAUDIO_IMPLEMENTATION`). Макрос реализации каждой библиотеки задавать **строго в одном** `.cpp`, исключая множественные определения. Не включать `.cpp` в другие `.cpp`.
3. **Изоляция интерфейсов:** предусмотреть собственные адаптеры загрузки изображения и аудиосистемы. У игровых объектов и публичных интерфейсов движка не должно быть требований включать `stb_image.h` или `miniaudio.h`. При замене библиотеки не должны меняться игровые сценарии.
4. **Границы применения:** `stb_image` используется для декодирования PNG в пиксели, после чего собственный код движка создаёт OpenGL-текстуру и управляет её ресурсами. `miniaudio` отвечает за аудиоустройство, декодирование поддерживаемого PCM WAV и микширование/воспроизведение; движок определяет свой API звуковых ресурсов и экземпляров воспроизведения. Собственный декодер PNG, протокол PipeWire/ALSA или аудиомикшер **не являются обязательными задачами**.
5. **Системные компоненты:** системные API, драйверы OpenGL, Win32/WGL, X11/GLX и доступные аудиосистемы Linux — допустимые **системные**, а не скачиваемые с проектом зависимости. Miniaudio может использовать штатные аудиобэкенды Linux; на машине пользователя должны быть доступные для работы звуковые средства. Нельзя обещать, что единственный исполняемый файл будет работать на любом Linux без установленных системных компонентов.
6. **Воспроизводимость:** новая чистая копия репозитория должна собираться без загрузки библиотек из интернета, Git submodules с обязательной инициализацией, FetchContent или внешнего менеджера пакетов. Проверять сборку Release и запуск на Windows/Linux; CMake должен выбирать нужные системные компоненты по ОС.
7. **Расширение списка:** никаких дополнительных сторонних библиотек без отдельного решения и обновления этого документа. Для шрифтов, физики, сцен, GUI и остальных механизмов используется собственная реализация.

### Архитектурные правила

1. **Сначала необходимый минимум, затем расширение.** Не добавлять ECS, визуальный редактор, встраиваемый язык сценариев, систему плагинов и другие крупные механизмы без подтверждённой необходимости. Для поведения объектов достаточно C++ API.
2. **Строгая граница платформенного кода.** Игровая логика не должна знать о заголовках, событиях, дескрипторах и структурах Windows/X11.
3. **Разделение ответственности.** Окно не занимается игровой логикой; рендерер не изменяет состояние объектов; физика не рисует; GUI не обрабатывает системные события напрямую.
4. **Явное владение ресурсами.** Понятный жизненный цикл объектов, текстур, звуков, подписок и системных дескрипторов. Не скрывать утечки за завершением процесса.
5. **Предсказуемое время.** Симуляция и анимация не должны зависеть от количества нарисованных кадров.
6. **Проверяемость.** Для алгоритмов — автоматические тесты; для графики и ввода — интерактивные демонстрации. Тестовый фреймворк извне не требуется; если тест использует PNG или звук, он вправе использовать уже включённые в проект `stb_image` и `miniaudio`.
7. **Две равноправные платформы.** Этап, затрагивающий ОС, нельзя считать завершённым без сборки и проверки на Windows и Linux.
8. **Единый, понятный API.** Каждая подсистема предоставляет минимальный публичный API. Новые подсистемы переиспользуют уже реализованные механизмы и не создают дубликаты математики, ввода, времени или файлового доступа.

### Ранние технические проверки

**PNG:** с локальным `stb_image` проверить загрузку из файла и из памяти, декодирование PNG в RGBA8, прозрачность, повреждённые данные, предельные размеры и освобождение буфера. Декодирование изолировать от управления GPU-текстурами. Другие форматы, которые умеет `stb_image`, не становятся обязательной возможностью движка.

**Аудио:** с локальным `miniaudio` проверить загрузку PCM WAV, запуск и остановку воспроизведения и одновременный вывод двух звуков в Windows и Linux. На Linux проверить доступный аудиобэкенд в реальной конфигурации (например, через ALSA, PulseAudio или совместимый слой PipeWire) и поведение при отсутствии устройства. Игровые объекты не должны зависеть от типов `miniaudio`.

### Результат каждого этапа

На выходе каждого этапа должны быть:

- **Работающая подсистема** с минимальным публичным API и определённым способом освобождения ресурсов.
- **Демонстрация** одного или нескольких реальных сценариев использования без зависимости от будущих подсистем.
- **Проверки** успешных и ошибочных сценариев (автотесты для алгоритмов, интерактивные проверки для окна, графики и аудио).

Для приёмки нужно выполнить проверки; отдельные протоколы и отчёты о них не требуются.

Сначала реализуется корректность и совместимость Windows/Linux, затем — удобство использования и оптимизации по результатам измерений. Если один этап объективно слишком крупный, его нужно разбивать на самостоятельные рабочие подэтапы, не меняя общий порядок.

### 01. Платформенный слой: окно и жизненный цикл

**Приёмка:** [x] Windows · [x] Linux

**Зависит от:** 00. **Получаем:** надёжное окно приложения с графическим контекстом.

- Создание и уничтожение окна, инициализация и освобождение контекста OpenGL, обработка частичной ошибки запуска.
- Заголовок, размеры клиентской области и изменение размеров окна. Минимальные ширина и высота клиентской области задаются приложением независимо друг от друга; по умолчанию обе равны нулю (дополнительных ограничений со стороны движка нет, действуют ограничения оконной системы).
- Два режима окна: фиксированный размер и размер, изменяемый пользователем. В изменяемом режиме пользователь может менять границы окна с соблюдением минимальных размеров. Игровая область на этом этапе остаётся фиксированной: изменение размеров окна не меняет её размеры и границы; политика масштабирования и расширения обзора относится к этапу 04.
- События закрытия, получения/потери фокуса, сворачивания и восстановления.
- Корректное обновление области вывода при изменении размера окна; снижение нагрузки при сворачивании.
- Управляемый выход из приложения; события пользовательского ввода не должны автоматически означать закрытие программы.

**Проверка:** окно многократно меняет размер, теряет и получает фокус, сворачивается и закрывается без зависаний, повреждённого изображения и утечек ресурсов на обеих ОС.

### 02. Ввод и система событий

**Приёмка:** [x] Windows · [x] Linux

**Зависит от:** 01. **Получаем:** единый способ принимать команды пользователя и распространять события.

- Клавиатура: удерживается / нажата в текущем кадре / отпущена в текущем кадре; при необходимости — повтор нажатия и ввод символов.
- Мышь: положение, перемещение, кнопки, нажатие/отпускание и колесо; координаты в пределах окна.
- Преобразование событий Win32 и X11 в единый набор событий движка; корректный сброс удерживаемых клавиш при потере фокуса. В публичных событиях не должно быть типов Win32/X11.
- События движка формируются при разборе нативных сообщений Win32 и событий X11, а не вычисляются сравнением снимков. Все полученные системные события окна должны проходить через платформенную обработку движка: преобразовываться в общие события либо обрабатываться внутри платформенного слоя, включая необходимую стандартную обработку ОС, без молчаливого отбрасывания.
- Определить формат общих событий и ответственность за состояние ввода; выделять общие модули в `engine` по мере появления работающей функциональности.
- Платформенный код передаёт переходы нажатия и отпускания клавиш и кнопок мыши, а общий код сохраняет их и предоставляет приложению одинаково на обеих ОС, даже если оба перехода произошли между двумя снимками состояния.
- События сохраняют историю изменений и порядок переходов, а снимок показывает итоговое состояние после их обработки.
- Очередь событий с сохранением порядка поступления.

**Дополнительная подсистема подписок:** необязательный слой движка поверх уже сформированных событий, вызывающий зарегистрированные обработчики. Он не зависит от GUI, обеспечивает предсказуемый порядок вызовов и безопасное добавление и удаление подписок во время обработки. Приложение может обходиться без него, напрямую разбирая события через существующий API.

**Проверка:** интерактивное демо отображает состояния клавиш, курсора и кнопок; удержание, однократное нажатие, отпускание и потеря фокуса ведут себя одинаково на Windows и Linux.
Демо использует подписки вместе со снимком ввода; общие тесты на обеих ОС проверяют порядок вызовов, отключение и изменение подписок во время обработки, время жизни обработчиков.

### 03. Управление приложением, временем и игровым циклом

**Приёмка:** [x] Windows · [x] Linux

**Зависит от:** 01–02. **Получаем:** предсказуемое обновление игры независимо от скорости рендеринга.

- Основной режим — одно обновление игрового мира на кадр с передачей переменного `deltaTime` (`dT`) в секундах. Скорости и длительности в игровой логике рассчитываются с учётом `dT`.
- Исключить большой скачок симуляции после паузы, сворачивания или длительной задержки: при продолжении сбрасывать отсчёт времени кадра, ограничивать максимальный `dT` при задержках.
- Независимые настройки ограничения FPS и вертикальной синхронизации; исключить конфликт нескольких ограничителей.
- Пауза/продолжение, управляемое завершение, порядок запуска и очистки подсистем.

**Проверка:** объект с постоянной скоростью за одинаковое реальное время проходит сопоставимый путь при разном FPS; после паузы или сворачивания и возвращения нет большого скачка симуляции.

### 04. Математика 2D, преобразования и камера

**Приёмка:** [x] Windows · [x] Linux

**Зависит от:** 03. **Получаем:** общий математический фундамент для всех подсистем.

**Проверка:** одновременно слышны несколько специально подготовленных WAV-звуков, меняется их громкость, работают пауза и остановка; одинаковый тест успешно запускается на Windows и поддерживаемой конфигурации Linux. **Без реального вывода звука на Linux этап не закрыт.** При сборке не должно требоваться скачивать или системно устанавливать miniaudio.
