# Требования к разработке

- Язык реализации: C++17.
- Графический API: OpenGL 1.1.
- Целевые платформы: Windows и Linux.
- Система сборки: CMake.
- Развивать движок небольшими последовательными изменениями.
- Писать понятный, читаемый код; избегать неоправданно сложных решений.
- Проверять новую функциональность после её добавления.
- Создавать или обновлять документацию только по прямому запросу пользователя.
- Тесты должны проверять уже реализованную функциональность через существующий API движка. Написание тестов не должно требовать изменения API движка или добавления в рабочий код движка специальных точек подключения, флагов или адаптеров только для тестирования.
- Не добавлять для тестов системные пакеты, библиотеки или инструменты сверх зависимостей, необходимых самому движку и сценам.
- Тесты должны быть независимы от демоприложений, игровых сцен и игровой логики.
- Использовать Git для фиксации изменений и возврата к предыдущим рабочим состояниям.
- Каждая задача должна оставлять проект в состоянии не хуже исходного: сохранять существующую функциональность, возможность сборки, качество и читаемость кода, а также согласованность архитектуры.
- Не добавлять специальную обработку гипотетических крайних случаев без выявленной практической необходимости. Каждая дополнительная проверка должна иметь ясную цель, связанную с реальным сценарием использования, требованием API или воспроизведённым сбоем.

## Работа с Git

- Писать сообщения коммитов в прошедшем времени, описывая выполненные изменения. Пример: «Упорядочена структура по roadmap и обновлены пути сборки».
- Перед началом каждого нового этапа разработки создавать ветку Git с именем `subsystem_nn`, где `nn` — двузначный номер подсистемы/этапа из `road map.md` (например, `subsystem_00`, `subsystem_01`). Разработку и коммиты этого этапа выполнять в этой ветке.
- Отправлять изменения разработки с ПК только в соответствующую ветку `subsystem_nn`. Никогда не отправлять изменения напрямую в `main`.
- Интегрировать изменения в `main` только через Contribute в веб-интерфейсе GitHub.
- Требования к рабочему процессу с Git распространяются как на разработчика, так и на ИИ-агентов.

## Стиль кода

- Объединять связанные данные и поведение в `class`, когда это делает код понятнее. Для простых наборов данных использовать `struct`.
- Все поля `class` должны быть `private`, все поля `struct` — `public`, включая статические поля и константы.
- Секции доступа располагать в порядке `public`, `private`, `protected`, пропуская пустые. В каждой секции сначала размещать методы, включая конструкторы и деструкторы, затем поля.
- Не объявлять именованные константы внутри объявления класса.
- Инициализировать переменные, включая поля и именованные константы, только в `.cpp`-файлах. В заголовочных файлах размещать объявления без инициализаторов.
- Реализация методов и функций должна распологаться в .cpp файлах.
- Передавать ошибки операций через выходные параметры-ссылки, а не через возвращаемые значения.  Использовать один объект ошибки или коллекцию ошибок в зависимости от потребностей операции.
- Предпочитать современные возможности C++17 и стандартной библиотеки там, где это целесообразно. Использовать стандартные строковые типы для текста и стандартные потоки для консольного вывода. Избегать символьных буферов произвольного фиксированного размера, если требуемый размер можно определить динамически.
- Управление ресурсами должно оставаться простым и соразмерным задаче. Использовать RAII и умные указатели там, где они дают конкретную пользу. Явные пары выделения и освобождения ресурсов допустимы в коротком, понятном коде работы с нативным API, если время жизни ресурсов ясно.
- Применять единый стиль ко всему собственному C++-коду проекта, включая обе платформенные реализации. Сохранять точное написание и требуемые сигнатуры внешних API, системных типов, макросов, констант и функций обратного вызова (Win32, X11, GLX, OpenGL, стандартная библиотека).
- Использовать четыре пробела для отступов; не использовать табуляцию. Открывающие фигурные скобки пространств имён, функций, классов и структур размещать на новой строке. Открывающие скобки блоков `if`, `else`, `for`, `while` и `switch` оставлять на той же строке, что и соответствующая конструкция. Всегда заключать тела управляющих конструкций в фигурные скобки.
- Использовать `camelCase` для собственных функций, переменных, полей и параметров; `PascalCase` — для собственных типов, перечислений, значений перечислений и именованных констант.
- Использовать осмысленные английские идентификаторы. Имена и типы, специфичные для ОС, оставлять внутри соответствующей платформенной реализации; независимые от ОС операции предоставлять через общий платформенный интерфейс.
- Ставить пробелы вокруг бинарных операторов и после запятых; не ставить пробел между именем функции и `(`. Связанные объявления и инструкции располагать вместе, логические части разделять пустыми строками.
- В списках инициализации не ставить пробелы сразу после { и перед }. В аргументах функций и вложенных инициализаторах явно указывать тип создаваемого объекта. Не повторять тип, если он уже указан в объявлении.
- Объявлять каждую переменную и константу на отдельной строке; не объединять несколько объявлений через запятую.
- Ограничивать область видимости переменных и констант минимально необходимой; объявлять их как можно ближе к месту использования.
- Использовать `const` для неизменяемых значений, `const T&` — для крупных объектов, доступных только для чтения, `nullptr` — для нулевых указателей и явные приведения типов (`static_cast`), когда требуется преобразование.
- Использовать `#pragma once` в заголовках проекта. Подключать заголовки проекта в кавычках, а системные и библиотечные заголовки — в угловых скобках. Предпочитать явное подключение заголовков прямых зависимостей.
- Писать краткие комментарии на русском языке для читателя исходного кода. Описывать фактическое поведение, контракты API, единицы измерения и существенные ограничения. Не пересказывать очевидные операции и не включать учебные объяснения синтаксиса или системных API.
- Не включать в комментарии историю и планы развития проекта, идеи, внутренние рассуждения, обоснования выбранных решений.
- Не вводить константы для значений, смысл которых уже понятен из имени переменной, поля или параметра функции. Давать отдельные имена только значениям с неочевидным назначением.
- В списках инициализации конструкторов размещать двоеточие на новой строке, а первый инициализатор — после него. Каждый следующий инициализатор размещать на отдельной строке, начиная её с запятой. Выравнивать все инициализаторы по вертикали.
- Не добавлять отступы для объявлений внутри пространств имён.
- В случаях, не оговорённых этими правилами, следовать общепринятым практикам C++17. Предпочитать простые и привычные решения, которые легко читать, проверять и изменять.
