# Требования к разработке

Документ является инструкцией для ИИ. Имеет три основные цели:
1. Обеспечить устойчивое развитие игрового движка на протяжении длительного времени. При добавлении и изменении функциональности сохранять корректность, работоспособность и существующее поведение подсистем движка и демосцен, за исключением изменений, предусмотренных задачей.
2. Поддерживать высокое качество кода. Сложность решений должна быть обоснована реальными потребностями проекта, а архитектура — развиваться по мере его роста, без преждевременного усложнения. Код должен оставаться понятным человеку и пригодным для самостоятельного сопровождения и развития.
3. Предотвращать ухудшения вследствие чрезмерно буквального применения инструкций и правил. Руководствоваться их назначением и практической пользой, а не только формальным соблюдением.

## 1. Технические ограничения

- Язык реализации: **C++17**.
- Графический API: **OpenGL 1.1**.
- Целевые платформы: **Windows и Linux**.
- Система сборки: **CMake**.
- Не менять технологии, версии стандартов или набор зависимостей без прямого согласования.

## 2. Приоритеты и принятие решений

- Приоритеты в порядке убывания: **обязательные ограничения и явные запреты**, **выполнение задачи**, **простота и читаемость**, **согласованность архитектуры**, **минимальность изменений**, **стилевые предпочтения**.
- Технические ограничения, явные запреты и правила работы с Git обязательны. Инженерные предпочтения применяются с учётом контекста; они не должны приводить к искусственному усложнению.
- Если правила противоречат друг другу или задача требует нарушения обязательного ограничения, сообщить о конфликте и предложить варианты; не обходить запрет молча.
- Предпочитать простые, распространённые для C++17 конструкции. Не добавлять код, абстракции и зависимости без конкретной пользы для текущей задачи.
- Допускается переработка архитектуры, если это приносит пользу для текущей задачи или устраняет конкретные архитектурные проблемы. Масштаб переработки должен быть соразмерен ожидаемой пользе. При изменении API движка необходимо согласованно адаптировать зависящие от него демосцены.
- При любых изменениях сохранять существующее внешнее поведение программы, за исключением изменений, явно предусмотренных задачей.
- Не приводить весь проект к новому стилю в рамках несвязанной задачи.

## 3. Выполнение задач ИИ-агентом

- Перед изменениями изучить относящиеся к задаче компоненты, их интерфейсы, зависимости и существующие аналогичные реализации. Не дублировать уже имеющуюся функциональность.
- Развивать движок **небольшими последовательными изменениями**. Решать поставленную задачу, а не предполагаемые будущие задачи.
- Не создавать интерфейсы, базовые классы, фабрики, менеджеры, универсальные обёртки или конфигурационные механизмы исключительно «на будущее».
- В область задачи входят изменения связанных сущностей, их интерфейсов и зависимостей, необходимые для целостной реализации текущей функциональности, даже если эти сущности прямо не перечислены в запросе. Допускается переработка или замена существующего решения, если она обоснована требованиями задачи и смыслом предметных сущностей. Минимальность изменений не должна приводить к обходным решениям, дублированию или сохранению неподходящей архитектуры.
- Не добавлять обработку гипотетических крайних случаев без практической причины. Проверять реальные границы системы, входные данные и результаты нативных API, если ошибка возможна и её обработка необходима по контракту.
- Не маскировать сбои фиктивными успешными результатами, молчаливым игнорированием ошибок или необоснованными значениями по умолчанию.
- Не создавать и не обновлять отдельную документацию без прямого запроса. Необходимые комментарии к изменяемому коду и корректировка затронутых контрактов API не считаются отдельной документацией.
- По завершении кратко сообщать: что изменено, что проверено фактически, что не удалось проверить и какие ограничения остались.

## 4. Проверка изменений и тестирование

- После добавления или изменения функциональности выполнять доступные относящиеся к ней проверки. По возможности проверять сборку и работу на затронутых платформах.
- Каждая завершённая задача должна сохранять существующую функциональность, собираемость, понятность и архитектурную согласованность проекта.
- Тесты должны проверять поведение через существующий API движка и не зависеть от демоприложений, игровых сцен или игровой логики.
- Не добавлять в рабочий код специальные флаги, точки подключения и адаптеры **только ради тестов**. Если тестирование выявило реальную архитектурную проблему, описать её отдельно; не менять архитектуру скрытно.
- Не добавлять для тестов системные пакеты, библиотеки и инструменты сверх зависимостей, необходимых движку и сценам, без отдельного согласования.
- Не ослаблять и не удалять существующие проверки, чтобы скрыть регрессию.
- Не утверждать, что тесты прошли, если они не запускались. Указывать точную область проведённых проверок, особенно когда проверялась только одна платформа.

## 5. Работа с Git

- Использовать Git для фиксации изменений и возврата к предыдущим рабочим состояниям.
- Перед началом **нового этапа разработки** создавать ветку `subsystem_nn`, где `nn` — двузначный номер этапа из `road map.md` (например, `subsystem_00`, `subsystem_01`). Если ветка нужного этапа уже существует, использовать её; не создавать новую при каждой мелкой задаче.
- Разработку и коммиты этапа выполнять в соответствующей ветке `subsystem_nn`. Не отправлять изменения непосредственно в `main`.
- Интегрировать изменения в `main` только через **Contribute** в веб-интерфейсе GitHub.
- Писать сообщения коммитов на русском языке в прошедшем времени с описанием выполненного изменения. Пример: «Упорядочена структура по roadmap и обновлены пути сборки».
- Не выполнять разрушительные операции Git, удаление чужих изменений или перезапись удалённой истории без явного разрешения.
- Правила Git одинаковы для разработчика и ИИ-агентов. Если доступ к Git или GitHub отсутствует, сообщить об этом, не изображая выполненные действия.

## 6. Структура C++-кода

- Объединять данные с поведением в `class`, когда это улучшает инкапсуляцию и ясность. Для простых наборов данных использовать `struct`.
- Поля `class` по умолчанию делать `private`; поля простых структур данных — `public`. `protected` и публичные поля классов использовать только при наличии конкретной архитектурной причины, а не ради сокращения кода.
- Секции доступа располагать в порядке `public`, `private`, `protected`, пропуская пустые. В секциях сначала размещать методы (включая конструкторы и деструкторы), затем поля.
- Реализации нетривиальных нешаблонных методов и функций преимущественно размещать в `.cpp`. Короткие очевидные методы, операции по умолчанию, `constexpr`-функции, шаблоны и другие определения, которым необходим или полезен заголовок, допускается размещать в `.h`.
- Не сжимать код искусственно ради лимита строк.
- Предпочитать инициализацию полей при объявлении для простых безопасных значений по умолчанию, включая стандартные типы и контейнеры. Инициализацию, зависящую от аргументов конструктора или требующую заметной логики, выполнять в конструкторе.
- Не оставлять поля неинициализированными без осознанной причины. Учитывать фактический порядок инициализации членов класса.
- Не вводить лишние обёртки, геттеры и сеттеры только для формального соответствия форме класса. В то же время не раскрывать внутреннее состояние без необходимости.

## 7. Ошибки и ресурсы

- Не навязывать единый способ сообщения об ошибках всем функциям. Для операций, уже использующих принятую в проекте схему (например, `bool` и параметр ошибки по ссылке), сохранять её согласованно.
- Если требуется вернуть и значение, и подробную ошибку, использовать наименее сложный подход, соответствующий текущему API.
- Использовать RAII и умные указатели там, где они уменьшают риск утечки и упрощают владение ресурсом. Избегать как неоправданных обёрток, так и неясного ручного управления временем жизни.
- Явные пары получения и освобождения ресурса допустимы в коротком линейном коде нативного API, если все пути выхода обеспечивают освобождение. При нескольких путях выхода предпочтителен RAII или иной простой гарантированный механизм очистки.
- Не скрывать ошибки Win32, X11, GLX или OpenGL, если от них зависит дальнейшая корректная работа.

## 8. Язык и зависимости

- Использовать современные возможности C++17 и стандартную библиотеку, если они дают простое, привычное решение. Не имитировать более новые стандарты без необходимости.
- Использовать стандартные строковые типы для текста и стандартные потоки для консольного вывода, если нативный API не требует другого представления.
- Избегать символьных буферов произвольного фиксированного размера, если размер данных можно определить динамически.
- Использовать `const` для неизменяемых значений, `const T&` для крупных объектов только для чтения, `nullptr` для нулевых указателей и подходящие явные преобразования (`static_cast` и другие — по назначению). Не применять явное приведение там, где корректно и понятно неявное.
- Ограничивать область видимости переменных и констант минимально необходимой; объявлять их рядом с использованием. Каждую переменную и константу объявлять отдельно.
- Не вводить именованные константы для значений, смысл которых уже очевиден из контекста. Использовать именованные константы, когда они помогают раскрыть назначение значения или упрощают сопровождение кода.
- Использовать `#pragma once` в заголовках проекта. Заголовки проекта подключать в кавычках, системные и библиотечные — в угловых скобках. Явно подключать прямые зависимости.
- Не добавлять зависимости, системные пакеты и вспомогательные инструменты без обоснованной потребности и согласования, когда они меняют требования к окружению.

## 9. Платформенная независимость

- Применять единый стиль к собственному C++-коду на обеих платформах.
- Сохранять точное написание, типы и необходимые сигнатуры внешних API, системных констант, макросов и callback-функций (Win32, X11, GLX, OpenGL и стандартная библиотека).
- Скрывать платформенно-зависимые API за интерфейсами игрового движка, не допуская их прямого использования за пределами платформенных реализаций.
- Не усложнять общий интерфейс абстракциями для платформ или сценариев, которые проект не поддерживает.

## 10. Форматирование и именование

- Использовать четыре пробела для отступов; табуляцию не использовать.
- Открывающие фигурные скобки пространств имён, функций, классов и структур размещать на новой строке. Для `if`, `else`, `for`, `while`, `switch` — на той же строке. Тела управляющих конструкций всегда заключать в фигурные скобки.
- Использовать `camelCase` для собственных функций, переменных, полей и параметров; `PascalCase` — для собственных типов, перечислений, значений перечислений и именованных констант.
- Давать осмысленные английские идентификаторы; не переименовывать внешний API и обязательные системные обозначения.
- Ставить пробелы вокруг бинарных операторов и после запятых; не ставить пробел между именем функции и `(`. Связанные объявления и инструкции группировать, логические части разделять пустыми строками.
- В списках инициализации в фигурных скобках не ставить пробелы сразу после `{` и перед `}`. При создании временных объектов в аргументах функций и вложенных инициализаторах всегда явно указывать тип создаваемого объекта. Не повторять тип, если он уже указан в объявлении переменной.
- В списке инициализации конструктора располагать `:` на новой строке, первый инициализатор — после него; следующие — на отдельных строках, начиная с запятой. Выравнивать инициализаторы по вертикали.
- Не добавлять отступы для объявлений внутри пространств имён.
- Не сокращать понятные имена и не уплотнять код только для уменьшения числа строк.

## 11. Комментарии

- Предпочитать понятный код комментариям. Добавлять краткие комментарии на русском языке только там, где без них трудно понять существенные особенности реализации.
- Пояснять неочевидные контракты, ограничения, единицы измерения, причины нестандартных решений и важные требования к порядку операций.
- Не пересказывать очевидный код и не добавлять учебные объяснения синтаксиса C++ или системных API.
- Не помещать в исходники внутренние рассуждения ИИ, историю переписки, планы развития и объяснения того, как выполнялась задача. Обоснования неочевидных технических решений допустимы, если они нужны для сопровождения кода.

## 12. Правило по умолчанию

В случаях, не оговорённых документом, следовать общепринятым практикам C++17 и существующим соглашениям проекта. Выбирать самое простое решение, которое корректно выполняет текущую задачу, понятно при чтении, безопасно управляет ресурсами и не препятствует дальнейшим изменениям. Не нарушать обязательные требования под предлогом упрощения; при реальном конфликте сообщить о нём.
