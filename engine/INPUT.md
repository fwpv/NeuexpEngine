# События, клавиатура и мышь

Реализован общий ввод этапа 02 поверх окна этапа 01. `input.h` содержит независимые
от ОС типы и накопитель `Engine::InputState`; `platform.h` публикует состояние окна
и ввода приложения. Win32/X11 преобразуют нативные сообщения в `Engine::Event`.
Код приложения не включает системные заголовки для работы с вводом.

## Использование

```cpp
Platform::Error error;
if (!Platform::processEvents(error)) {
    Platform::reportError(error, false);
    // Перейти к завершению приложения и Platform::shutdown().
}

const auto& input = Platform::getInput();
const auto space = input.key(Engine::Key::Space);
// space.down — удержание; space.pressed/released — переходы этого кадра.
// Также доступны Platform::isKeyDown/isKeyPressed/isKeyReleased.
const auto left = input.button(Engine::MouseButton::Left);
const auto& mouse = input.mouse();

for (const auto& event : Platform::getEvents()) {
    switch (event.type) {
        case Engine::EventType::TextInput:
            // Вставить event.text (UTF-8) в сфокусированный текстовый элемент.
            break;
        case Engine::EventType::MousePressed:
            // Проверить попадание event.x/event.y в элемент интерфейса.
            break;
        case Engine::EventType::MouseReleased:
            // event.canceled отменяет drag/нажатие, не активируя кнопку GUI.
            break;
        default:
            break;
    }
}
```

Приложение вызывает `processEvents` один раз перед обработкой ввода кадра. Вызов
сбрасывает предыдущие `pressed/released`, движение, колесо, текст и список событий,
затем публикует полученные сообщения. Удержание и положение сохраняются.
Win32-сообщения, пришедшие синхронно между вызовами, сохраняются до публикации.
Чтение API не опрашивает ОС и не потребляет события. Ссылки и указатели на данные
кадра следует использовать до следующего `processEvents`, `initialize` или `shutdown`.

Нажатие и отпускание между кадрами дают **оба** флага `pressed` и `released`,
при итоговом `down == false`. Для нескольких переходов и последовательности GUI
используйте события: снимок не хранит число или порядок переходов. Системный повтор
приходит как `KeyPressed` с `repeat == true`, не создавая нового `pressed`.
Повтор определяется по уже удерживаемой в этом окне клавише, одинаково на обеих ОС.
После отмены при потере фокуса первое новое сообщение нажатия начинает новый переход,
даже если ОС продолжает физический автоповтор. Сам возврат фокуса переходов не создаёт.

`InputState::beginFrame/handleEvent` — общий алгоритм накопления. Он также позволяет
приложению воспроизводить записанные события в отдельном экземпляре. Изменять
платформенный экземпляр напрямую нельзя. До инициализации и после завершения API
возвращает пустой ввод. Все платформенные функции вызываются из одного потока;
поддерживается одно окно.

## Клавиатура и текст

- `Key` обозначает физическую позицию по US-клавиатуре, независимо от текущего языка:
  A–Z, цифры, пунктуация, управляющие клавиши, навигация, F1–F24, цифровой блок,
  левый/правый Shift, Control, Alt и Super, системные клавиши и ISO-backslash.
- Windows использует scan codes и расширенный бит, X11 — имена XKB. Физически
  отсутствующие клавиши не порождают событий. Неизвестная позиция даёт `Key::Unknown`;
  событие сохраняется, состояние неизвестной клавиши всегда пустое.
- `Modifiers` в событиях клавиатуры/мыши и снимке содержит Shift, Control, Alt,
  Super, CapsLock и NumLock. Левая и правая стороны доступны через `key()`.
  Для вставки текста следует использовать `TextInput`, включая ввод через AltGr.
- В Linux CapsLock/NumLock обновляются уведомлениями XKB, а не инвертированием
  по физической клавише. `LockStateChanged` передаёт только `modifiers.capsLock`
  и `modifiers.numLock`; остальные модификаторы и удержание клавиш сохраняются.
  Это учитывает снятие блокировки при отпускании и переназначение клавиш.
  В Windows состояние блокировок читается через `GetKeyState` при обработке ввода.
- `TextInput::text` — подтверждённая строка UTF-8; один commit может содержать несколько
  символов. `input.text()` объединяет commits текущего кадра. Enter, Tab, Backspace и
  другие управляющие клавиши обрабатываются через клавиатурные события.
- Windows использует Unicode-сообщения, собирает пары UTF-16 и принимает `WM_UNICHAR`.
  Счётчик повторений учитывается и для `WM_CHAR`, и для `WM_UNICHAR`.
  Некорректные кодовые точки заменяются U+FFFD. Незавершённая пара отменяется при потере фокуса.
- Linux использует XIM и `Xutf8LookupString`, включая Compose/dead keys, фильтрацию
  незавершённого ввода и получение commit произвольной длины. Внешний метод ввода
  зависит от настройки системы; при недоступном сервере пробуется локальный XIM.
  Если создать контекст ввода невозможно, инициализация сообщает ошибку и освобождает ресурсы.
  Служебный `KeyPress` XIM с `keycode == 0` запрашивает готовый текст и не создаёт
  физического нажатия `Key::Unknown`. Ошибка получения `XNFilterEvents` прерывает
  запуск с освобождением контекста ввода и метода ввода.
- Отображение незавершённой IME-композиции предоставляется системным методом ввода.
  Собственный preedit внутри виджета и позиционирование окна кандидатов этим API пока
  не предоставляются. Для обычных элементов GUI этапа 10 достаточно текущих событий.

Linux требует XKB (часть X11) и настроенную локаль `LC_CTYPE`. При запуске применяется
локаль окружения и XIM-модификаторы, при завершении восстанавливаются прежние значения.
Дополнительных сторонних библиотек или пакетов для подсистемы и её тестов нет.

## Мышь и отмена ввода

Положение задаётся в пикселях клиентской области: начало сверху слева, X вправо,
Y вниз. Преобразование в координаты GUI/мира и поддержка DPI относятся к этапу 04.
При drag координаты могут быть отрицательными или выходить за размер окна.

Поддерживаются пять обычных кнопок: Left, Right, Middle, Back, Forward; вход и выход
курсора; движение; колесо по X/Y. `MouseState::deltaX/deltaY` — сумма перемещений
этого кадра, `Event::deltaX/deltaY` — отдельный переход между сообщениями движения.
Первое известное положение задаёт начальную точку. Выход из окна не обрывает
накопление перемещения; потеря фокуса сбрасывает начальную точку.

Колесо измеряется в шагах: положительное X вправо, Y вверх. Windows сохраняет дробные
шаги; core X11 предоставляет целые шаги кнопками 4–7. Отпускание кнопки колеса не
создаёт дополнительный шаг. Положение события колеса приведено к клиентской области.

Во время нажатия Windows захватывает мышь до отпускания последней кнопки; X11
предоставляет автоматический захват для настоящих ButtonPress. Это позволяет
закончить drag за пределами окна. Потеря захвата Windows даёт `MouseCaptureLost`.

Потеря фокуса, сворачивание и уничтожение окна отменяют удержание клавиш и кнопок.
После события-причины следуют синтетические отпускания с `canceled == true`.
GUI должен отменить активное нажатие/перетаскивание без выполнения действия click.
Возврат фокуса сам по себе не создаёт нажатий. Удерживавшиеся вне окна модификаторы
не восстанавливаются опросом клавиатуры: требуются новые переходы внутри окна.

## Оконные события и границы этапа

Общие события включают FocusGained/Lost, WindowResized, WindowMinimized/Restored,
CloseRequested и WindowDestroyed. Их полезные данные описаны в `input.h`.
`Event::time` — монотонное время получения сообщения движком, в секундах; это не
аппаратное время нажатия и не гарантия интервала между действиями при зависшем потоке.

`CloseRequested` сохраняет действующий контракт этапа 01: окно автоматически не
уничтожается, завершение выбирает приложение. Обычная клавиша, включая Escape,
не закрывает окно. Стандартные системные сочетания обрабатывает ОС. Win32 передаёт
необработанные сообщения `DefWindowProcW`; X11 передаёт события фильтру XIM,
обновляет mapping/свойства окна и обрабатывает его жизненный цикл. Остальные
уведомления X11 не требуют аналога DefWindowProc: например, перерисовку обеспечивает
цикл приложения, а чужие свойства не меняют состояние единственного окна движка.

Список событий относится к одному кадру.

## Необязательные подписки

`events.h` и отдельная CMake-цель `engine_events` предоставляют `EventDispatcher`
поверх готовых `Event`. Подключите библиотеку только к приложениям, использующим
подписки. Платформа и `InputState` работают независимо от неё; глобального
диспетчера и автоматической рассылки нет.

```cpp
#include "events.h"

// Данные должны жить дольше обработчика, который ссылается на них.
std::string text;
Engine::EventDispatcher dispatcher;
auto subscription = dispatcher.subscribe(Engine::EventType::TextInput,
    [&text](const Engine::Event& event) {
        text += event.text;
    });

// После успешного processEvents, один раз за кадр:
for (const auto& event : Platform::getEvents()) {
    dispatcher.dispatch(event);
}

subscription.disconnect(); // Повторное отключение безопасно.
```

- `subscribe(handler)` слушает все типы, `subscribe(type, handler)` — один тип.
  Пустая функция возвращает отключённую подписку.
- Сохраняйте возвращённый `EventSubscription`: уничтожение отключает обработчик.
  Подписку можно перемещать, включая хранение в коллекции, но нельзя копировать.
  Присваивание перемещением отключает предыдущую подписку получателя.
  `connected()` сообщает, действуют ли подписка и её диспетчер.
- Все операции выполняются в одном потоке. Вызов синхронный, порядок обработчиков
  соответствует регистрации. Порядок событий задаёт вызывающий код; повторный
  `dispatch` того же события повторяет рассылку.
- Добавленная во время рассылки подписка действует со следующего `dispatch`.
  Отключённая пропускается сразу, даже если её очередь ещё не наступила.
  Самоотключение позволяет текущему вызову завершиться. Захваты функции
  освобождаются при отключении, а у выполняемой функции — после выхода из неё.
- Вложенный `dispatch` заканчивается до продолжения внешнего и видит актуальные
  подписки, включая только что добавленные. Приложение отвечает за завершение
  рекурсивной рассылки. Исключение обработчика выходит из `dispatch`, прерывая
  текущую рассылку; диспетчер остаётся пригодным к дальнейшему использованию.
- Подписка может пережить диспетчер и станет отключённой. Уничтожение диспетчера
  в обработчике отключает остальных; текущий обработчик завершится.
  Диспетчер нельзя копировать и перемещать.
- Событие доступно обработчикам только для чтения и должно жить до конца рассылки.
  При рассылке `Platform::getEvents()` обработчики не должны вызывать
  `processEvents`, `initialize` или `shutdown`: эти операции инвалидируют данные
  кадра. Запросы таких операций следует выполнить после обхода событий.

Владелец GUI может хранить подписки полями, объявленными после используемых ими
данных: поля уничтожаются в обратном порядке. Захват `this` не продлевает жизнь
объекта; подписки нужно отключить до уничтожения данных, к которым обращается
обработчик. Для GUI достаточно подписать корневой экран и внутри него выбирать
элемент с учётом фокуса, координат и приоритетов этапа 10. Диспетчер доставляет
событие всем подходящим обработчикам; маршрутизацию между GUI и игрой организует
приложение. Отдельные диспетчеры позволяют разделять экраны и сцены.

Реализация хранит функции через `std::function`; на рассылку создаёт снимок
указателей на подписки, поэтому изменение списка не инвалидирует обход.
Стоимость рассылки и временная память линейны по числу подписок. Отключение сразу
освобождает функцию; пустые записи удаляются при следующей регистрации или рассылке.
Такой механизм рассчитан на подписчиков уровня экранов и подсистем небольшой
2D-игры; обход дерева виджетов остаётся внутри GUI.

## Демо и проверки

После обычной сборки запустите `build/input_demo.exe` в Windows или `build/input_demo`
в Linux. Сетка показывает клавиши в порядке перечисления `Key`; нижние пять ячеек —
кнопки мыши. Зелёный цвет обозначает нажатие, синий — удержание, оранжевый — отпускание.
Заголовок показывает фокус, последнюю клавишу, координаты, движение, колесо и текст.
Последняя клавиша и текст обновляются через подписки; индикаторы используют
существующий снимок ввода. Демо показывает совместное использование обоих API.
В Windows демо запускается без консоли; ошибки показываются в диалоге.
Закройте демо кнопкой окна. Существующее `circle`
продолжает использовать совместимый `Platform::isKeyDown`.

`scripts/test.bat` и `scripts/test.sh` включают:

- `event_dispatcher`: порядок и фильтрация, владение и перемещение подписок,
  отключение и регистрация в обработчике, вложенная рассылка, исключения,
  уничтожение диспетчера, освобождение захватов и интеграция с `InputState`.
  Один общий исходник собирается на Windows и Linux без окна и новых зависимостей.
- `input_state`: все значения клавиш и кнопок, короткие/повторные переходы, обе стороны
  модификаторов, порядок событий, сброс кадра, неизвестные коды, координаты, дробное
  колесо, отмена ввода, Unicode и оконные данные без графической сессии.
- `platform_input`: независимая программа с настоящим окном. Отправляет нативные
  сообщения целевому окну, проверяет преобразование клавиш/мыши, текст, фокус,
  события размеров/сворачивания/закрытия/уничтожения и повторный запуск.
- `platform_input_legacy_repeat` на Linux: те же сценарии при старом autorepeat X11.
- `platform_input_constructor_rollback` на Linux: ошибка поиска окна после открытия
  X11-соединения; проверяется парный вызов `XCloseDisplay` при отказе конструктора теста.

В Windows проверяются UTF-16/UTF-32, некорректные суррогаты, захват мыши и дробное
колесо, включая повторения `WM_UNICHAR`. В Linux — настоящий локальный XIM для ASCII,
а также тестовые подмены результата XIM для длинных Unicode commits, служебного
`keycode == 0` и фильтрации, без установки IME-сервера. Уведомления XKB проверяются
без изменения блокировок клавиатуры рабочего стола.
`platform_startup_rollback` дополнительно проверяет отказ `XGetICValues` с освобождением
XIC/XIM в Linux и отказ чтения/несоответствие выбранного формата пикселей в Windows.
Windows проверяет наличие OpenGL для окна, двойной буферизации и RGBA через
`DescribePixelFormat` перед установкой формата. Разрядность цвета и глубины —
предпочтения запроса: меньшая разрядность и отсутствие буфера глубины не запрещают
запуск. Тест отдельно проверяет принятие таких описаний; реальная доступность
форматов зависит от драйвера.

Для текущего 2D-вывода используется одна конфигурация: RGBA с двойной буферизацией.
Требования к размеру буфера глубины нет на обеих ОС. `present` обменивает буферы;
отдельного однобуферного режима и цепочки повторных попыток выбора формата нет.
Все подмены находятся в тестах и настройках их сборки. Для проверки физических
клавиш Linux-тест предполагает обычную PC-клавиатуру с US-группой; F13–F24, которых
нет в стандартном pc105, дополнительно покрыты общим тестом состояния.
Тесты не перемещают реальный курсор и не посылают ввод другим приложениям.

Приёмка этапа 02 остаётся открытой до завершения остальных его требований и проверки
обеих ОС. Наличие Linux-тестов само по себе не означает их успешного запуска.
