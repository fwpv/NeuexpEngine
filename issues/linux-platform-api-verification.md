# Отложенная проверка платформенного API на Linux

Статус: ожидает доступа к Linux с графической сессией. Дата: 21 октября 2026 года.
Область: подсистемы 01–02, X11/GLX, XKB и XIM.

Исправления находятся в коммите `ca939ab`. Их проверка на Windows завершена:
16 тестов прошли. Это не подтверждает сборку и выполнение Linux-веток.
Документ описывает оставшуюся проверку и не означает приёмку Linux.

## Что уже обнаруживалось

- Поиск тестового окна через `XFetchName` не соответствовал заголовку
  `UTF8_STRING`; заменён на `XGetWMName`.
- Физическое имя клавиши Menu могло быть `COMP` с псевдонимом `MENU`;
  добавлено разрешение псевдонимов XKB.
- Тест изменения размера ожидал результат за один кадр; добавлено ограниченное
  ожидание события с нужными размерами (до 500 мс, проверка каждые 10 мс)
  и проверка всех событий кадра. Получение события сразу завершает ожидание.
- Чужое окно исчезало во время поиска, вызывая `BadWindow`; тестовый поиск
  пропускает эту ошибку только для чтения свойств и дерева на своём соединении.
- Ручное инвертирование CapsLock/NumLock заменено уведомлениями XKB.
- Служебный `KeyPress` XIM с кодом 0 больше не создаёт физическое нажатие.
- Отказ `XGetICValues` при чтении `XNFilterEvents` прерывает запуск с очисткой.
- Выбор GLX visual не требует буфера глубины: используется одна конфигурация
  RGBA с двойной буферизацией, без резервного однобуферного режима.
- `platform_keyboard` проверяет синтетические переходы клавиши и фокуса в одном
  целевом окне. Ранее переходы клавиши смешивались с реальным переключением фокуса,
  и тест мог завершаться с `Focus loss failed.` из-за вмешательства оконного менеджера.
  Настоящее переключение фокуса по-прежнему проверяет `platform_window`.

Первые четыре проблемы были выявлены по отчётам запуска на Linux. Остальные
требуют подтверждения после внесённых исправлений. В автоматических тестах часть
ответов XIM и уведомления блокировок XKB подменяются, поэтому нужны и проверки
реального ввода.

## Окружение и сборка

Записать дистрибутив, архитектуру, версии компилятора и CMake, оконный менеджер,
тип сессии, локаль, метод ввода и использование виртуальной машины. Полезные команды:

```bash
git rev-parse HEAD
uname -a
cat /etc/os-release
cmake --version
c++ --version
locale
printenv DISPLAY XDG_SESSION_TYPE XDG_CURRENT_DESKTOP XMODIFIERS
```

Проверять в X11. Если доступен XWayland, его результат записать отдельно.
Нативный Wayland не входит в текущую область поддержки. Использовать уже имеющиеся
зависимости проекта; дополнительные пакеты ради тестов не устанавливать.

Из корня репозитория создать отдельный каталог сборки, чтобы не использовать
кэш Windows из общей папки виртуальной машины:

```bash
cmake -S . -B build/linux-api-check -G "Unix Makefiles" \
  -DCMAKE_BUILD_TYPE=Release -DBUILD_DEMOS=ON -DBUILD_TESTING=ON
cmake --build build/linux-api-check --parallel 4
ctest --test-dir build/linux-api-check --output-on-failure
```

Ожидание: сборка без новых предупреждений, все зарегистрированные тесты проходят.
Пропуск теста из-за отсутствия дисплея не подтверждает проверку графической части.
Сохранить при сбое `build/linux-api-check/Testing/Temporary/LastTest.log`.

Для поиска редких гонок отдельно выполнить:

```bash
ctest --test-dir build/linux-api-check --output-on-failure \
  -R '^platform_input' --repeat until-fail:100
ctest --test-dir build/linux-api-check --output-on-failure \
  -R '^platform_(startup_rollback|external_destroy)$' --repeat until-fail:100
```

Ожидание: ни одного падения, зависания, необработанной ошибки X11 или ошибки очистки.
Повторный прогон служит проверкой устойчивости, а не заменяет разбор причины сбоя.

## Проверки, требующие реальной Linux-сессии

1. **CapsLock и NumLock.** Проверить включение и выключение, в том числе вторым
   нажатием с отпусканием, переключение при потерянном фокусе и возврат в окно.
   Сопоставить `InputState::modifiers()` с фактическими блокировками ОС.
   Уведомление `LockStateChanged` не должно создавать нажатий клавиш или сбрасывать
   удерживаемый Shift/Control/Alt. Для наблюдения флагов использовать отдельную
   диагностическую программу через публичный API: заголовок `input_demo` их не показывает.
   Если в системе уже настроено переназначение CapsLock, проверить и его: физическое
   нажатие само по себе не должно менять флаг блокировки.

2. **Физические клавиши и раскладки.** Проверить Menu, обе стороны модификаторов,
   цифровой Enter, NumLock, Pause и PrintScreen. При смене US/русской раскладки
   физический `Key` сохраняется, а `TextInput` соответствует вводимому тексту.
   Смена раскладки во время работы не должна оставлять устаревшую карту или удержание.

3. **XIM.** Запустить `build/linux-api-check/input_demo` с настройками текущей
   сессии и отдельно с локальным методом ввода:

   ```bash
   XMODIFIERS=@im=none ./build/linux-api-check/input_demo
   ```

   Проверить доступные Compose/dead keys, кириллицу, AltGr и, если внешний IME уже
   установлен, подтверждение композиции из нескольких символов. Подтверждённый
   текст должен приходить однократно, без ложного `KeyPressed(Unknown)` от служебного
   кода 0. Потеря фокуса отменяет незавершённую композицию. CTest запускает проверки
   ввода с `XMODIFIERS=@im=none` и не подтверждает работу внешнего IBus/Fcitx.

4. **Окно и порядок событий.** Повторять изменение размера, сворачивание,
   восстановление, потерю фокуса и закрытие. При потере фокуса удерживаемые клавиши
   и кнопки отпускаются с `canceled == true`. Их удержание не восстанавливается
   само при возврате. Размеры в событиях соответствуют клиентской области.
   Оконный менеджер может выдавать промежуточные размеры и задерживать результат.

5. **Мышь.** В `input_demo` проверить все пять кнопок, отпускание за границей окна,
   отмену перетаскивания при потере фокуса и колесо по доступным осям. Боковые кнопки
   Back/Forward ожидаются как X11-кнопки 8/9. Если они не доходят до уже установленного
   `xev`, сначала проверить передачу ввода виртуальной машиной/настройки системы.
   Отсутствие событий в `xev` само по себе не устанавливает точную причину.

6. **Повторный запуск и примеры.** Несколько раз запустить и штатно закрыть
   `input_demo` и `circle`; проверить отсутствие ошибок X11/GLX и очистки.
   Тесты отказов должны сохранять исходную ошибку и позволять повторную инициализацию.

7. **Графическая конфигурация.** Подтвердить выбор RGBA visual с двойной
   буферизацией. Глубина не задаётся как обязательное требование; наличие
   буфера глубины зависит от драйвера. Однобуферные конфигурации не поддерживаются.

Наблюдения можно выполнять вручную; автоматическую проверку вести через тесты,
журналы и публичный API. Не использовать управление по скриншотам или computer vision.

## Наблюдение: редкая пауза при сворачивании в виртуальной машине

21 октября 2026 года пользователь сообщил о паузе примерно на пять секунд
в сценарии сворачивания на Linux. Вероятное имя теста — `platform_window_minimize`
(в сообщении указано `platform_windows_minimize`; такого имени в CMake нет).
После паузы выполнение продолжилось, все тесты завершились успешно.
Точная операция, длительность и причина задержки пока не установлены.

Статус: наблюдение, без подтверждённой ошибки движка. Возможные причины для проверки —
оконный менеджер, графический драйвер и приостановка/нехватка ресурсов виртуальной
машины. Успешный результат тестов сам по себе не объясняет эту задержку.

При следующем доступе к Linux сохранить подробный журнал повторного запуска:

```bash
ctest --test-dir build/tests-only -V -R '^platform_window_minimize$' \
  --repeat until-fail:100 --output-log build/tests-only/minimize-repeat.log
```

Сравнить время медленного прогона с обычными, сохранить журнал и отметить,
оставались ли отзывчивыми другие приложения гостевой ОС и хост, была ли VM
активна и требовались ли действия пользователя для продолжения. Если пауза
повторится, определить конкретный блокирующий вызов уже на Linux. До этого
изменения алгоритма сворачивания и новые резервные режимы не обоснованы.
Диагностические отметки в код теста для этого наблюдения не добавлены.

После успешной проверки обновить отметку приёмки Linux в `road map.md`.
